# ArtMotion Kit (한국어 출력판)

## 결과물 언어: 한국어

- 화면 글자, 자막, 내레이션, 스토리보드, 납품 메모는 한국어로 쓴다. 사용자가 다른 언어를 지정하면 그 언어로.
- `references/` 문서는 중국어 원문 그대로다. 그대로 읽고 따르되, 거기 나오는 중국어 예시 문구를 화면에 옮기지 않는다. 아래 「참고 문서 길잡이」에서 언제 무엇을 읽을지 고른다.
- 한글 글꼴: `l10n/apply.sh`가 아래 패밀리에 한글을 붙여 두었다. 한국어 글자는 이 패밀리로만 쓴다.
  - `PuHui-Medium` / `PuHui-Bold` / `PuHui-Heavy` / `PuHui-Black`: 본고딕(Noto Sans KR) 500/700/800/900
  - `NotoSansSC`(가변 굵기): Noto Sans KR 가변, `NotoSerifSC`(가변 굵기): Noto Serif KR 가변
  - `LXGWWenKai-500`: 손글씨 개구체(Gaegu). 화이트보드 문법이 쓴다.
  - Cinzel, Playfair 같은 라틴 장식 글꼴에는 한글이 없다. 한글을 넣으면 시스템 글꼴로 조용히 바뀐다(엔진이 `console.error`로 잡아 렌더가 실패한다).
- 한글 글꼴은 KS X 1001 상용 2,350자만 들어 있다. 「똠」「햏」처럼 빠진 글자가 있으면 `uv run l10n/scripts/build_fonts.py --src <원본 ttf 폴더> --text "똠햏"`로 다시 만들고(원본은 github.com/google/fonts 의 `ofl/notosanskr`, `ofl/notoserifkr`, `ofl/gaegu`), `l10n/apply.sh ko`를 다시 돌린다. 11,172자 전체가 필요하면 `--full`.
- 줄바꿈: 한글은 어절(띄어쓰기) 단위로 끊긴다. 한 줄에 넣을 말은 띄어쓰기 없이 붙이지 않는다.

## 먼저 등급을 정한다

- **자유 등급**: Claude Opus 5.5 이상 모델. 이 문서 전체를 쓴다. 라우팅 표, 좁은 다리, 열린 땅. 라이브러리를 마음대로 조합하고 렌더러도 직접 써도 된다. 납품은 똑같이 `scripts/deliver.py`를 거치고 빨간불이면 납품하지 않는다. 시작 전에 스토리보드를 한 장 쓰기를 권한다. 린트는 돌려도 되고 안 돌려도 된다.
- **레일 등급**: 그 밖의 모델, 또는 자기가 어떤 모델인지 모르겠으면 이 등급이다. 아래 길 하나만 걷는다. 스토리보드를 먼저 쓰고 손을 댄다. 이 길에서 이름을 부른 파일만 읽는다.
  1. **스토리보드 쓰기**: `<프로젝트>/storyboard.md`. 표 앞에 세 줄로 화풍을 잠근다. `화풍:`(한 문장, 영상 전체에 이것 하나), `팔레트:`(`references/色板.md`의 한 세트 이름 또는 색 3–6개, 파랑·보라 금지), `캐릭터:`(없음 / 손과 뒷모습만 / 프레임 라이브러리 <경로>, 먼저 `references/角色精细度.md`를 읽는다). 표는 한 줄에 한 컷:

     ```markdown
     | 시간 | 사물 | 동작 | 카메라 | 화면 글자 | 방법 |
     |---|---|---|---|---|---|
     | 0–3 | 손과 식빵 한 봉지 | 손이 봉지를 뜯고 손끝이 푸른 곰팡이에서 멈춘다 | 정지 | | scenes/kitchen.js |
     ```

     카메라 칸 어휘: 정지 / 천천히 밀기 / 빼기 / 가로 이동 / 빠른 밀기 / 내리꽂기 / 컷. 아래 「연출 요구: 카메라」를 따른다. 빠른 밀기와 내리꽂기는 강세에만. 이 칸을 쓰기 전에 `references/镜头语言.md` 1~4절을 읽는다. 화면 글자는 한글 16음절(영어 8단어) 이하, 비워도 된다. 첫 3초는 제목이 아니라 구체적인 작은 장면이다(손 한 쌍이나 물건 하나가 주제와 관련된 일을 한다). 영상 전체를 구체적인 예 하나로 끌고 간다. 한 컷 2–6초. 글자가 주인공인 컷은 30% 이하. 이웃한 두 컷은 구도를 바꾸고 화풍은 바꾸지 않는다.
  2. **린트 통과**: `python3 <skill>/l10n/scripts/lint.py <프로젝트>/storyboard.md`(내레이션 원고가 있으면 `--script <프로젝트>/script.txt`를 붙여 화면 숫자와 내레이션 숫자가 같은지 본다). 원본 `scripts/storyboard_lint.py`를 한국어 표에 맞춰 돌리는 래퍼다. 결과 메시지는 중국어로 나온다. 빨간불이 있으면 스토리보드를 고치고 다시 돌린다. 빨간불이 남아 있으면 코드를 쓰지 않는다.
  3. **스토리보드대로 한 컷씩**: `cp -R <skill>/scripts/engine <프로젝트>/engine`. 컷마다 `shotNN.mp4` 하나, 모든 컷은 같은 크기·같은 fps(기본 1920×1080@30).
     - 파라미터 클립: `references/09-视频动画语法.md` 2절 선택표와 해당 `references/动画语法/<문법>.md`의 「起手必查(시작 전 점검)」을 읽는다. `examples/<문법>.json`에서 구조만 베끼고 내용은 베끼지 않는다. 화면 글자는 스토리보드 칸 그대로(한국어). `uv run --with playwright python <프로젝트>/engine/render.py --spec shotNN.json --out shotNN.mp4`. **파라미터 클립 하나는 최대 8초**, 넘으면 여러 컷으로 나눈다. 한국어 예시: `l10n/demo/y3_whiteboard.ko.json`.
     - scenes: 미술 양식 화면(고흐, 픽셀 등)이나 클립 문법으로 못 그리는 사물. `references/风格配方/INDEX.md`와 양식 카드 한 장을 읽고 `scenes/<id>.js`를 써서 `eras.js`에 등록한다. `render.py --solo <id> --from 0 --to <초> --fps 30 --no-counter --out shotNN.mp4`. 한국어 자막판 예시: `l10n/demo/eras_ko.js`.
     - 화풍 하나로 끝까지: 모든 클립 spec에 같은 `"theme"`(스토리보드 팔레트 줄, 쓰는 법은 `references/色板.md`), 클립 문법은 최대 2가지. scenes도 같은 팔레트만. 컷마다 `--stills 0.5,2 --out stills/shotNN`로 정지 프레임을 뽑아 한 줄로 늘어놓고 스토리보드와 대조한다. 다른 영상에서 가져온 것처럼 보이는 컷은 화풍에 맞춰 다시 만든다.
  4. **이어 붙이기**: 컷과 컷은 하드 컷. `shotNN.mp4`가 있는 폴더에서:
     ```sh
     for f in shot*.mp4; do printf "file '%s'\n" "$f"; done > shots.txt
     ffmpeg -y -f concat -safe 0 -i shots.txt -r 30 -c:v libx264 -crf 16 -pix_fmt yuv420p -an film.mp4
     ```
     내레이션이 있으면: `ffmpeg -i film.mp4 -i narration.wav -map 0:v -map 1:a -c:v copy -c:a aac -shortest film_vo.mp4`. 전환 효과가 필요하면 전부 scenes로 만들고 컷 순서대로 `eras.js` 구간표에 넣는다(구간마다 `dur` 초와 `transition`). 전체 모드 `render.py --out film.mp4`로 한 번에 뽑는다.
  5. **QA**: 클립마다 `uv run <skill>/scripts/qa.py --spec shotNN.json --out <프로젝트>/qa/shotNN`. scenes가 있으면 `qa.py --project <프로젝트>/engine --ids <id,…> --out <프로젝트>/qa/scenes`. 뽑은 프레임을 아래 「망치는 여섯 가지」와 하나씩 대조한다.
  6. **납품**: `uv run <skill>/scripts/deliver.py film.mp4 --root <프로젝트> --qa <프로젝트>/qa/<점프가 가장 많은 컷> --out output/`. 빨간불이면 납품하지 않는다. 스크립트는 영상을 복사하지 않으니 출력된 고칠 점대로 고치고 다시 렌더·다시 실행한다. 초록·노란불이면 영상을 복사하고 `output/交付说明.md`(납품 메모)를 쓴다. 길이·게이트·QA·검수 여부 같은 사실 부분은 스크립트가 중국어로 쓰고 지문이 붙는다. 고치지 않는다. 너는 「制作说明(제작 메모)」 절에만 한국어로 덧붙인다. 쓴 문법과 방법, 나머지 컷의 QA 결론(한 컷에 한 줄), 노란불 항목마다 이유, 망치는 여섯 가지 자가 점검. 독립 검수를 맡겼다면 검수자가 먼저 결론을 `<프로젝트>/审片/*.md`에 쓰게 한 뒤 실행한다(폴더 이름 `审片`은 스크립트가 찾는 이름이라 그대로 둔다).

## 너는 누구인가

이 영상의 감독이자 콘티 작가, 원화가, 애니메이터, 편집자다. 붓 대신 코드로 그린다. 완성본의 기준: 관객이 컷마다 무슨 이야기인지 알아보고 계속 보고 싶어 한다. 미술 양식을 쓸 때는 누구 그림인지 한눈에 알아보고, 그림이 살아 있다. 이미지가 넘어가는 슬라이드가 아니다.

먼저 감독이다. 아래 두 절은 감독이 영상 전체에 내리는 요구다. 카메라를 어떻게 움직이고 화풍을 어떻게 고르는지. 구체적인 초·횟수·파라미터는 references에 있고, 숫자마다 언제 적용되고 언제 무시해도 되는지 적혀 있다. 숫자는 출발점이다. 더 나은 설계가 있으면 그렇게 하고, 만든 뒤 정상 속도로 한 번 본다.

## 연출 요구: 카메라

카메라는 문장부호다. 문장마다 붙이는 꾸밈이 아니다. 움직이기 전에 세 가지를 답한다. 관객이 지금 어디를 봐야 하고, 지금 화면 크기에서 그게 잘 보이는가. 이 움직임은 넘어가기인가 강세인가. 바로 앞 컷의 카메라 동작은 무엇이었나.

- **잘 보이면 움직이지 않는다.** 화면이 스스로 움직일 때(실사 영상, 그려지고 있는 선, 자라는 곡선)는 카메라를 멈춘다. 관객이 글을 읽는 동안도 멈춘다. 해설 영상에 오래 멈춰 있는 구간이 있는 건 정상이다. 버벅임이 아니다.
- **넘어갈 때는 느리게, 강세에만 빠르게.** 다음 디테일로 시선을 데려갈 때는 천천히 밀기, 여러 물건 사이를 오갈 때는 가로 이동, 전체를 보여 주거나 단락을 닫을 때는 빼기. 빠른 밀기·내리꽂기·휩은 강세라서 공개, 반전, 핵심 숫자, 웃음 포인트에만 쓴다. 한 영상에서 셀 수 있을 만큼만.
- **들어가면 나온다.** 밀고 들어간 뒤에는 빼서 나오거나 옆으로 비키거나 하드 컷으로 화면 크기를 바꾼다. 세 컷 연속 안으로 밀지 않는다. 한 컷에 소재 한 장을 꽉 채울 때 「한 장 넘기고 한 번 밀기」가 되기 쉽다. 102초짜리 해설 영상에서 약 48번을 전부 안쪽으로 밀었더니 원작자가 「줌인이 너무너무 많다. 횟수도 많고 리듬도 너무 빨라서 전혀 매끄럽지 않다」고 했다.
- **영상 전체가 한 가지 박자여서는 안 된다.** 컷마다 똑같이 천천히 밀면 「완전히 PPT 넘기는 느낌」이 나고, 컷마다 한 번씩 빠르게 밀면 너무 빠르고 거칠다. 원인은 같다. 컷마다 같은 동작이다. 카메라는 단락의 감정을 따라간다. 담담하게 설명할 땐 안정적으로, 전환과 절정에서만 빨라진다. 뮤직비디오 한 편에도 원작자는 「카메라 워크와 전환이 단조롭고 메마르고, 다양성도 감정 표현도 없다」고 했다.
- **안 움직인다고 좋은 것도 아니다.** 「배경이 너무 밋밋해서 보고 싶은 마음이 전혀 안 든다」는 평을 받고 버려진 판이 있다. 화면 안에서 계속 무슨 일이 일어나야 한다. 사물이 움직이고, 소재 자체가 움직이고, 새것이 드러나고, 카메라가 시선을 이끈다. 천천히 밀기, 가로 이동, 빼기도 전부 움직임이다. 빠르냐 느리냐와 움직이냐 안 움직이냐는 다른 문제다.
- **미술 양식 화면은 따로: 그림이 계속 살아 있어야 한다.** 한 장면에 주 동작 하나와 반복 모티프 동작 2개, 카메라는 느리게 흘러도 된다. 원작자는 「그림 사이에 전환만 넣는」 방식을 거부했다. 「원본은 시대마다 1초 남짓이지만 그림 속 요소는 완전히 흐르고 있다. … 너무 많이 잃는다.」
- 동작 종류, 각각의 길이, 횟수를 언제 신경 쓸지는 `references/镜头语言.md`를 읽는다. 엔진의 `CAM.track`은 동작을 안 쓰면 천천히 밀기다. 파라미터 클립의 highlight도 기본은 천천히 밀기다. 빠른 밀기는 spec 최상위 `data`에 `"camera": "snap"`을 쓸 때만이다(`{"data": {"camera": "snap"}}`. spec 최상위(grammar와 같은 층)에 직접 쓰거나 어떤 cue의 data에 쓰면 적용되지 않고 오류도 나지 않는다).

## 연출 요구: 화풍 고르기

화풍은 내용을 섬긴다. 손에 있는 소재가 무엇이고 이 구간에서 무엇을 설명해야 하는지 먼저 보고, 그다음 그리는 법을 고른다.

- **실제 소재가 있으면 소재가 주 화면이다.** 스크린샷, 사진, 영상, 원문, 제품이 실제로 만든 결과물을 화면 가득 놓고, 코드는 설명·주석·카메라만 맡는다(`MD.cover` 꽉 채우기, `MD.print` 인화지를 조사 책상에 올리기, `MD.label` 검은 바탕 찢긴 라벨. 이미지가 없으면 바로 오류). Vox 조사 책상이나 화이트보드로 소재를 엮는다. 정말 소재가 없는 구간만 통째로 코드로 그리거나 AI로 생성한다. 거의 전부 AI로 생성한 기술 해설 장편을 본 원작자의 평: 「시각적인 느낌이 아주 안 좋다.」
- **설명할 내용으로 문법을 고른다.** 원리와 추론은 화이트보드·3b1b, 숫자와 추세는 금융 차트, 경험담과 개그는 storytime, 미술과 시대는 양식 카드. 선택표는 09번 문서 2절, 문법별 카메라 기조는 `镜头语言.md` 3절.
- **한 영상에 화풍 하나, 팔레트 하나, 마지막 프레임까지.** 사람·동물·소품도 같은 붓질로 그린다(모네 풍 뮤직비디오에 벡터 도형 고양이와 손을 넣었다가 「모네 화풍과 잘 안 맞는다」는 말을 들었다). 모든 파라미터 클립에 같은 `theme`, scenes도 그 색만. 깔끔하게 통일됐지만 조금 슬라이드 같은 영상이, 컷마다 화풍이 바뀌는 콜라주보다 낫다. 파랑·보라 그라데이션, 진보라 별하늘, 네온 청보라는 쓰지 않는다(원작자: 「이런 건 정말 AI slop이다」). 사용자가 파랑·보라를 직접 요구하면 예외이고, 납품 때 `--allow-blue-purple "이유"`.
- **입체적이고 풍성한 쪽으로 생각한다.** 단면 파노라마 애니메이션에 대한 원작자의 평: 「입체적이고 풍성하고, 한 번에 아주 전면적이고 압도적인 장면을 본다.」 사용자가 거절한 방향은 다시 내놓지 않는다.
- **새 방향은 세 가지를 먼저 보여 주고 고르게 한다.** 같은 프레임, 세 가지 구도. 색만 바꾼 셋은 안 된다(아래 「세 방향 관문」).

## 가장 흔히 망치는 여섯 가지 (시작 전, 납품 전에 한 번씩 대조)

1. **넘기는 PPT**: 고정 머리글과 쪽 번호, 요점이 한 줄씩 페이드인, 컷마다 같은 카메라 동작(매번 천천히 밀기, 또는 매번 한 번 빠르게 밀기), 마지막은 가운데 명언 카드. → 페이지 틀을 없앤다. 한 컷에 화면 사건 하나. 카메라는 「연출 요구: 카메라」대로, 이웃 컷은 다른 동작, 들어가면 나온다. 끝은 주인공이나 주 사물의 동작으로(주머니에 넣기, 책 덮기, 빼서 전체 보기). 글자는 그림 속 사물 위에 써도 된다. 린트는 마지막 컷이 글자 카드인지, 세 컷 연속 안으로 미는지, 강세가 너무 많은지 본다. deliver.py는 측정한다. 컷 안 움직임이 거의 없으면 빨간불이고 영상을 내보내지 않는다. 밀기가 너무 잦으면 노란불.
2. **예시 베끼기**: 예시 영상, 샘플 spec, 양식 샘플의 구도·캐릭터·소재가 그대로 완성본에 들어감. → 방법만 배우고 구도와 사물은 주제에 맞춰 새로 설계한다.
3. **구체적인 사물이 없다**: 추상 개념을 글자와 아이콘으로만 씀. → 스토리보드 줄마다 구체적인 사물과 그 동작을 쓴다. 사물을 못 쓰는 줄은 아직 만들지 않는다.
4. **죽은 배경, 빈 화면**: 넓은 단색이나 별하늘 바탕이 그대로이고 가운데 작은 부분만 움직임. 또는 화면 전체가 단색·검은 화면·빈 풍경만 남고 주인공이 없음. → 주체를 화면 절반 이상으로 키우고 배경은 내용 따라 바꾼다. 컷마다 주인공이나 주 사물이 화면에 있다. 차트 컷의 바탕은 앞뒤 컷과 같은 색 계열(t3의 `theme`). 린트는 사물 칸이 빈 화면·단색·검은 화면인지 보고, film_gate(deliver.py가 먼저 돌림)는 완성본 중간에 0.3초 이상 이어지는 빈 화면을 찾아 빨간불을 켠다.
5. **실제 소재가 있는데 코드로 그림**. → 스크린샷, 사진, 영상, 원문을 화면 가득 놓고 코드는 설명·주석·카메라만.
6. **한눈에 AI 티**: 파랑·보라 그라데이션 바탕, 진보라 별하늘, 네온 청보라 빛. 컷마다 화풍이 바뀌는 콜라주(만화 사람 → 어두운 코드 화면 → 별하늘 아이콘 → 흰 바탕 막대그래프 → 웹 캡처). 코드로 그린 SD 캐릭터와 흰 로봇. 얼굴 달린 동전·공·이온. → 표 앞에서 화풍 하나와 팔레트 하나(`references/色板.md`)를 잠그고 모든 클립에 같은 `theme`. 캐릭터는 AI 생성 프레임으로 납품 기준을 넘기거나 손과 뒷모습만(`references/角色精细度.md`). 린트는 화풍 잠금, 팔레트 색, 캐릭터 줄을 보고, deliver.py는 파랑·보라 바탕이 전체의 30%를 넘으면 빨간불이다.

## 내레이션 (선택, 필요할 때만)

- 기존 녹음이 있으면 그대로 쓴다: `python3 scripts/capabilities.py use-audio --audio <파일> --out <프로젝트>/vo/01.wav`.
- 새로 만들어야 하면 macOS 내장 음성을 쓴다. 계정·키가 필요 없고 기기 밖으로 아무것도 나가지 않는다.
  `python3 <skill>/l10n/scripts/say.py --text "고흐의 하늘은 왜 소용돌이칠까" --out <프로젝트>/vo/01.wav [--fit 3.2] [--match 원본.wav]`
  한글이 있으면 한국어 음성(Yuna 우선), 없으면 미국 영어 음성(Samantha 우선)을 고른다. `--list`로 설치된 음성 확인. 다른 음성은 시스템 설정 > 손쉬운 사용 > 음성 콘텐츠에서 내려받는다.
- 원본의 Volcengine 음성 복제(중국 클라우드, 유료)는 사용자가 직접 요청하고 계정을 가진 경우에만 `references/capabilities.md`대로. 기본으로 켜지 않는다.
- 소리 없는 애니메이션이면 음성 설정을 시작하지 않는다. 오디오만 필요한 작업이면 화면 설계나 검수를 시작하지 않는다.

## 이미지 (선택)

이미지가 필요하면 `references/images.md`를 읽는다. 기존 이미지는 바로 가져온다. 생성은 지금 세션에 실제로 있는 도구와 사용자 허락으로 고른다. 스크립트가 호출 계획을 내고, 에이전트가 도구를 실행한 뒤 검수하고 프로젝트로 복사한다. 이미지가 필요 없으면 설정하지 않는다. 생성을 금지했으면 다른 공급자로 우회하지 않는다.

## 좁은 다리: 글자 그대로 따른다

- **사람은 AI 생성 프레임, 코드는 합성**(`references/10-角色.md`). 코드로 사람 얼굴이나 로봇을 그리지 않고 사물에 얼굴을 달지 않는다(`references/角色精细度.md`).
- **예시는 방법을 이해하는 데만.** 예시 영상, 샘플 spec, 양식 샘플의 구도·캐릭터·소재를 완성본에 그대로 넣지 않는다.
- **재현은 메커니즘을 배우는 것이지 픽셀 복사가 아니다.** 장면·움직임·전환의 규칙을 뽑아 새 주제에 쓴다.
- **세 방향 관문**: 새 캐릭터 해석이나 새 화풍 방향은 세 가지를 먼저 보여 주고 고르게 한다. 세 방향은 구도가 달라야 하고 색만 바꾸면 안 된다. 양식을 지정받아도 면제되지 않는다.
- **결정성**: 모든 난수에 시드를 쓴다. 같은 시각을 두 번 렌더하면 픽셀까지 같아야 한다.
- **독립 검수**: 납품 전에 제작에 참여하지 않은 에이전트에게 완성본만 보고 문제를 찾게 하고, 결론을 `<프로젝트>/审片/*.md`에 쓴다(deliver.py는 여기만 본다).
- 캐릭터가 미성년자(예: 17세)면 옷은 단정한 긴 옷. 이미지 모델에 「짧은 치마」를 쓰면 심사에서 통째로 거절된다.

## 열린 땅: 출발점이지 할당량이 아니다

`风格配方/`의 카드 36장(총표 `风格配方/INDEX.md`, 「재료 층」과 「시대 표본」 두 표)은 실제로 해 본 파라미터와 함정이지 유일한 그리는 법이 아니다. 샘플 35개와 `assets/全风格总览.jpg`는 같은 방 구도를 쓴다. 미술사 스피드런 영상의 메커니즘이지 이 양식들의 구도가 아니다. 새 주제는 주제에 맞게 구도를 새로 잡는다. 표에는 양식마다 현재 품질과 약점이 적혀 있으니, 다음에 그 양식을 쓸 때 먼저 약점을 넘어선다. 더 나은 렌더러가 있으면 쓰고, 결과를 원작이나 레퍼런스와 나란히 보여 준다. 새 양식을 만들면 카드를 추가한다.

## 엔지니어링

`scripts/engine/`은 통째로 복사해 쓰는 완전한 프로젝트다(엔진, 전환 라이브러리, 그리기 라이브러리, 캐릭터 뼈대, 양식 scene 35개, 렌더러. 유튜브 해설 문법 라이브러리 8개, 예시 영상 8편 `demos/`, 파라미터 클립 `clip.html`+`clips/`는 09번. 긴 두루마리 예시 `demos/long_scroll/`은 11번. 내레이션 전체 영상 참고 코드 `reference_films/spacex/`는 캐릭터와 오디오를 직접 준비해야 하며 폴더 README 참고). 새 영상: 프로젝트의 `engine/`으로 복사하고 `eras.js` 구간표를 고치고 `scenes/<id>.js`를 쓴다.

```sh
E=<프로젝트>/engine
uv run --with playwright python $E/render.py --solo <id> --stills 0,0.3,0.6 --out renders/<id>     # 한 구간 정지 프레임
uv run --with playwright python $E/render.py --out film.mp4 --audio music.wav                     # 전체
uv run --with playwright python $E/render.py --spec clip.json --out clip.mp4                      # 파라미터 클립
python3 $E/compare.py --a ref.mp4 --b film.mp4 --times 1.5,2.0 --out compare.jpg                  # 나란히 비교
uv run scripts/analyze/breakdown.py --video ref.mp4 --out breakdown/                              # 분해 지도
```

글꼴은 `scripts/engine/lib/fonts/`(woff, 라이선스는 같은 폴더 `LICENSES.md`, 한글 글꼴은 `l10n/fonts/OFL-*.txt`). 의존성: [uv](https://docs.astral.sh/uv/), ffmpeg(출력과 분해), Playwright Chromium(처음에 `uv run --with playwright playwright install chromium`).

## 검수

납품 전 세 가지, 순서대로. ① `uv run scripts/qa.py --project <engine>`(파라미터 클립은 `--spec`. 안정성/효율/움직임/매끄러움과 글자 프레이밍 단서. 2초 안의 단조롭고 매끄러운 밀기·빼기·가로 이동은 카메라 이벤트로 치고 점프로 세지 않는다). ② 독립 에이전트가 완성본만 보고 검수, 결론은 `<프로젝트>/审片/`. ③ `uv run scripts/deliver.py film.mp4 --project <engine>(또는 --spec) --out output/`. deliver.py는 먼저 `film_gate.py` 게이트를 통과해야 한다. 빠른 움직임 프레임 비율 < 0.035면 빨간불(복사 안 함, 0이 아닌 종료 코드), < 0.06이면 노란불. 통과해야 영상을 복사하고 납품 메모를 쓴다. 길이, 게이트 항목, 가장 나쁜 30초 구간, QA 결과, 검수 기록 여부는 스크립트가 쓰고, 검수가 없으면 「没派审片(검수 안 함)」이라고 쓴다. 사실 부분에는 지문이 있어 `deliver.py --verify`로 수정 여부가 드러난다. 게이트의 나머지 두 가지: 완성본 중간에 0.3초 이상 이어지는 거의 단색, 윤곽선이 거의 없는 빈 화면은 빨간불과 타임코드. 파랑·보라 바탕이 전체의 30%를 넘으면 빨간불(주제가 파랑·보라를 요구하면 `--allow-blue-purple "이유"`로 노란불, 이유는 납품 메모에). 게이트가 막는 건 이 세 가지뿐이다. 페이지 틀, 베이지 바탕 작은 그림, 앞은 빡빡하고 뒤는 느슨한 리듬, 컷마다 화풍이 바뀌는 콜라주는 못 막으니 프레임을 뽑아 「망치는 여섯 가지」와 다시 대조한다. 정지가 많은 건 병이 아니다. 해설 영상에는 원래 오래 멈춘 구간이 있으니 정지 관련 숫자로 판단하지 않는다. 「밀기 횟수」 노란불은 너무 자주 밀었다는 뜻이니 정상 속도로 한 번 본다. 카메라가 매끄러운지는 정지 프레임으로는 안 보인다. 반드시 정상 속도로 완성본을 한 번 본다. 밝은 바탕에 자막 없는 완성본은 `uv run --with numpy python scripts/subzone_gate.py film.mp4`로 그래픽이 자막 영역을 침범하는지 본다(질감 바탕에는 맞지 않는다). 경험은 먼저 `07-正面经验.md`.
